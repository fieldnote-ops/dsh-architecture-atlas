DOCS / 04 / LIFECYCLE ENGINE

Fiber ·
Effect · Inject

Fiber 把一个插件实例从“对象”变成“可协调的生命周期”：它知道插件想去哪、现在确认到哪、依赖是否满足，以及卸载时要逆序撤销什么。

DSH v0.1.0-rc.5Cordis 4.0.1生命周期引擎
一句话模型

inject 说明插件何时可运行，effect 记录运行造成的变化和返回路径，Fiber 则把两者放进一个有目标态、已提交态和异步汇合点的六态机器。

它解决什么问题

插件并不是“调用一次 apply 就永远存在”。它可能在依赖尚未就绪时等待，在异步初始化中失败，在服务消失时先让依赖者退出，也可能被新配置替换。若这些过程只靠布尔值 loaded 表达，更新很容易撞上正在进行的装载或卸载。

Fiber 把中间过程物化成状态，并把插件产生的效应归到具体运行 epoch。Loader 因此可以等待一个可观察的稳定结果，而不是猜测异步回调何时真正结束。

最重要的心智转换：卸载不是“调用 dispose 的一个瞬间”，而是一段需要停止供给、排空依赖者、再执行逆操作的状态转移。

六个工程状态

00 / PENDING等待依赖

插件仍在注册表中，但 inject 条件未满足，runner 尚未激活。

01 / LOADING执行回调

setup / apply 正在产生效应，生命周期尚未提交为 ACTIVE。

02 / ACTIVE服务可用

当前 runner epoch 活跃，提供项可被依赖者解析。

03 / UNLOADING排空与撤销

停止新的供给和效应，等待依赖者退出，再运行 disposer。

04 / FAILED失败被记录

同步或异步错误成为可观察结果，已经收集的效应需要回滚。

05 / DISPOSED离开注册表

uid 被清除，此 Fiber 不再参加后续协调。

这六个状态不是严格的单向流水线。例如依赖暂时消失，ACTIVE 可以经过 UNLOADING 回到 PENDING；新配置到来，旧运行 epoch 会退出，新 epoch 再进入 LOADING。FAILED 也不是进程级崩溃，它让失败停留在相关 Fiber 上，供 Loader 判断更新结果。

这一层如何工作

1. target 与 committed 分开

target 表达协调器希望 Fiber 到达的视图，committed 表达已经被生命周期确认的视图。二者存在差异时，Fiber 才知道需要 reload、unload 或继续等待。这样，新配置即使已经出现，也不会在候选尚未稳定时冒充运行事实。

2. inject 把读取边界写进图

插件声明自己依赖哪些服务键。所需服务全部可用时，它可以从 PENDING 进入 LOADING；服务消失时，运行时能沿依赖关系要求使用者先退出。这也是为什么配置行顺序不等于加载顺序。

3. effect 同时写下动作与逆

ctx.effect(callback) 执行副作用，并收集 callback 返回的 disposer。注册服务、订阅事件、打开资源时都应留下对应的撤销动作。多个 disposer 按 LIFO 组合：后建立的关系先拆除，避免先移走底层资源后，上层清理还在访问它。

APPLY产生效果

写注册表、订阅事件或取得外部资源，同时返回逆操作。

ACCUMULATE归入 Fiber

disposer 进入当前 runner epoch 的逆序链。

REVERSE逐项撤销

卸载时从最后一项开始执行，直到本轮效果被排空。

4. 卸载先断供，再排空依赖者

如果提供者一边卸载，使用者还可以继续取得它的服务，就会产生新的悬空依赖。因此 Fiber 进入 UNLOADING 后先停止对外供给，拒绝创建新的效应；依赖者感知服务不可用并开始退出；等下游沉淀后，提供者才继续逆序清理。

5. inertia 与 settlement 给协调器一个等待点

生命周期转移可能触发更多转移：一个服务激活会唤醒依赖者，一个服务退出又会让多个插件回到等待。运行时需要等这一连串反应平静下来，才能向 Loader 报告候选拓扑的稳定结果。这里的“稳定”是当前变更下没有待处理转移，不代表系统以后不会再变化。

关键规则

  • 一个插件实例对应一个 Fiber。配置身份、runner epoch、依赖和效应都围绕它协调。
  • PENDING 是正常状态。缺少依赖时等待，不应在插件内部反复轮询服务。
  • ACTIVE 只描述当前已提交运行态。候选配置存在不代表它已经生效。
  • UNLOADING 拒绝新效应。否则清理过程会不断产生新的待清理项。
  • disposer 使用 LIFO。后产生的依赖通常建立在先产生的资源之上，应该先拆。
  • 依赖者先于提供者完成退出。这让下游清理仍能在必要时观察到一致的旧视图。
  • 框架保证调用顺序，不保证外部世界一定可逆。如果 disposer 写错、遗漏，或外部 API 本身不可逆，恢复仍不等价。

常见误解

误解

Fiber 就是轻量线程，负责并发执行插件代码。

更准确的理解

这里的 Fiber 是插件生命周期与依赖协调单元，不是操作系统线程或通用任务调度器。

误解

调用 unload 后，插件已经立即消失。

更准确的理解

它先进入 UNLOADING：停止供给、等待依赖者，再逐项执行 disposer。

误解

使用 effect 就能自动保证所有副作用完全恢复。

更准确的理解

框架能保证逆操作的归属与顺序；逆是否正确、外部系统是否可逆，仍取决于实现。

误解

FAILED 意味着整个 DSH 进程都必须退出。

更准确的理解

失败被物化在相关 Fiber 上，协调器可以限制影响范围并决定恢复策略。
