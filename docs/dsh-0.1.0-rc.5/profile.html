DOCS / 01 / DECLARATIVE LAYER

Profile ·
Bundle · Patch

声明层不负责“按顺序启动插件”，而是把基础能力、运行模式与用户选择组合成一份目标拓扑。

DSH v0.1.0-rc.5commit 47f9438声明层
一句话模型

把配置文件想成“系统最后应该长什么样”的清单。Profile 组合 Bundle，Patch 按条目 id 覆盖；真正的激活顺序由服务依赖决定。

它解决什么问题

一个 Agent 运行时往往同时需要会话、提示词、工具、模型适配器、循环、沙箱和界面。如果把它们写进一段启动脚本，运行模式一多，脚本就会充满条件分支。DSH 把“选哪些组件、各自用什么配置”留在声明层，让同一组插件可以被 web、headless 等不同入口重组。

这样做也划清了职责：声明层只给出目标，Loader 才负责把当前运行态协调到目标态。配置的书写顺序因此不是生命周期顺序。

阅读锚点：向下看时追踪配置如何成为目标态；不要把 YAML 行序当成插件调用栈。

这一层如何工作

01 / BASE基础 Bundle

放入多数运行模式都会需要的插件条目与默认配置。

02 / MODE模式 Bundle

web-app 或 headless 继续增加、替换适合当前入口的条目。

03 / USER用户 Patch

最后按相同 id 覆盖，形成实际交给 Loader 的目标集合。

覆盖以条目为单位

同一 id 再次出现时，后写条目获胜。对 config 而言，这是整行替换，不是任意深度的对象合并。后一个条目没有写出的字段，不应被想当然地从前一个条目继承。

顺序由依赖图产生

条目可以先被发现、模块可以先被导入，但插件只有在自己声明的服务依赖可用后才能进入激活过程。于是“先写 Agent Loop、后写 LLM”并不意味着 Loop 会在没有 LLM 的情况下运行。

关键规则

  • Profile 是组合入口。它选取 Bundle，并叠加适合一次运行的 Patch。
  • Bundle 是可复用配置片段。base、web-app、headless 表达不同粒度的默认能力。
  • id 是覆盖锚点。更新配置时先看条目是否仍代表同一个插件实例。
  • config 按整项替换。需要保留的字段要在后一个条目中明确写出。
  • 配置顺序不授予运行时特权。服务可用性和 Fiber 协调才决定激活。

常见误解

误解

Patch 会像常见配置库一样，把嵌套对象逐字段深合并。

更准确的理解

相同 id 的后一个配置条目覆盖前一个；依赖旧字段时，应在新条目中明确保留。

误解

配置写在前面，就一定先加载、先提供服务。

更准确的理解

声明只描述目标集合。运行时通过 inject 和服务可用性计算激活关系。
