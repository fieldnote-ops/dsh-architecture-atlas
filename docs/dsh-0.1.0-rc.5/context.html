Cordis
Context · Γ∞

Context 不是传参方便用的容器。它同时承载服务解析、隔离边界、拦截信息、事件与效果归属，是插件彼此发现的统一运行时。

一句话模型

插件不直接抓取另一个插件实例，而是通过 ctx.<service> 读取能力；Context 在访问点解析当前隔离范围内可用的服务，并把访问纳入依赖与生命周期约束。

它解决什么问题

“Everything is a plugin” 只有在插件之间没有隐藏的特权通道时才成立。如果 Agent Loop 直接 import 某个 LLM 实现，或者工具系统把注册表放进全局变量，替换插件就会断开一条看不见的依赖。

Context 把共享能力实体化为服务键：sessions、systemPrompt、tools、agents、agentLoop、llm。提供者把能力写入上下文，使用者声明需要哪些键；运行时据此判断插件何时可以激活。

读 Context 时要同时看“值”和“关系”。一个服务键不只是对象存储位置，也是提供者、使用者、隔离范围与生命周期之间的连接点。

这一层如何工作

01 / PROVIDE服务进入 Context

插件在自己的 Fiber 生命周期内提供服务，并让注册动作带上可撤销效果。

02 / RESOLVE代理在访问点解析

ctx.llm 等读取会考虑当前 Context、隔离和拦截条件。

03 / REACT可用性驱动生命周期

服务出现或消失后，依赖者被重新判断：激活、保持、等待或卸载。

统一，但不等于所有东西全局共享

Γ∞ 表达一套可统一推理的上下文模型，并不意味着所有插件都读写同一个全局对象。Context 可以派生，isolate 让同一服务键在不同范围解析到不同实例，intercept 则附带横切信息。统一的是机制，不是值域。

事件是另一种扩展接缝

除了直接服务调用，Cordis 还提供 emit、waterfall、parallel、serial 等事件操作。它们让多个插件围绕同一事件扩展行为；但复杂异步流与流式模型输出并没有被论文中的转移规则完整形式化。

关键规则

  • 共享能力先成为服务键。跨插件访问不应依赖具体实现的内部对象。
  • 读取发生在 Context 代理上。运行时可以在访问点解析隔离范围并检查依赖。
  • 提供服务属于某个 Fiber。当 Fiber 卸载，服务供给和相关效应应一起撤销。
  • 隔离改变解析结果。同名服务可以在不同派生 Context 中指向不同提供者。
  • 直接 import 会绕开图。框架无法自动协调未被服务键和效应表达的隐藏关系。

常见误解

误解

Context 就是依赖注入容器，负责从名字拿到对象。

更准确的理解

它还承载隔离、拦截、事件、效应归属和生命周期反应，是运行时语义的一部分。

误解

所有插件都使用 Context，就不会再出现耦合。

更准确的理解

直接 import、全局写入和未返回 disposer 的外部副作用，仍然可以绕开边界。
