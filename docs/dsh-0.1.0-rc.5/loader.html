协调层比较“现在有什么”和“目标是什么”，把配置差异翻译成尽量少的生命周期动作。

DSH v0.1.0-rc.5commit 47f9438协调层
一句话模型

Loader 不是按文件顺序执行插件的脚本。它先准备候选、等待相关 Fiber 稳定，再提交新状态；候选失败时尽可能保留或恢复旧状态。

它解决什么问题

当用户只修改一个插件的配置时，重启整个 Agent 既慢，也会丢失无关组件的内存态；直接在原对象上改，又可能把系统留在“新旧各一半”的状态。协调层负责识别变化类型，只触发必要动作，并把异步生命周期纳入一次可判断成败的更新。

Include 负责把分散配置纳入同一棵配置结构；Loader 维护配置条目与插件 Fiber 的对应关系；HMR 在允许的入口监听模块变化并请求替换。三者都服务于同一个目标：让运行态向声明态收敛。

这一层的关键词不是“加载”，而是“协调”。导入模块只是准备工作，相关生命周期是否已经稳定，才决定更新能否提交。

这一层如何工作

01 / DIFF识别变化

围绕 id、name、isolate、intercept、config、disabled 判断新增、移除或更新。

02 / SETTLE准备候选

导入并验证候选，让相关 Fiber 完成激活、失败或卸载等异步转移。

03 / COMMIT提交或恢复

候选稳定后更新缓存与运行态；失败则回到旧插件或旧配置。

字段变化对应不同成本

disabled 变化可能只需要停用或恢复现有条目；config 变化可能走配置更新或重载；name、isolate 等身份和边界变化通常需要更完整地重建。协调器的价值，就在于不把所有差异都粗暴地当成全量重启。

汇合点把异步变成可提交结果

插件回调可以创建异步任务，服务变化还会唤醒依赖者。Loader 因此需要等待生命周期沉淀（settlement），才能知道候选拓扑最终是 ACTIVE、PENDING 还是 FAILED。

关键规则

  • 先按条目身份找差异。id 稳定时，协调器才有机会做最小更新。
  • 模块导入不等于插件激活。依赖未满足时，Fiber 可以保持 PENDING。
  • 更新包含等待阶段。相关生命周期没有沉淀，就不能把半完成候选当成新事实。
  • 组内更新可以并发。失败应被限制在相关候选范围，不必让无关插件一起重启。
  • 该版本的 web-app 关闭共享 HMR。浏览器侧重载边界尚未被当作已验证能力。

常见误解

误解

热更新就是重新 import 一次文件，然后用新导出替换旧导出。

更准确的理解

模块变化只是起点。旧效应要撤销，依赖者要排空，候选还要等待生命周期稳定。

误解

只要新插件导入成功，更新就已经成功。

更准确的理解

导入成功不代表依赖满足、apply 成功或异步效应稳定；提交判断发生得更晚。
