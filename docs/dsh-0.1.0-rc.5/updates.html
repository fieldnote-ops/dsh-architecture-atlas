更新与恢复

DSH 把更新当成一次运行态协调：先识别真正变化的部分，再等待相关生命周期稳定，最后提交新状态或保留旧状态。

什么会触发更新

Profile 或 Patch 变化后，Loader 比较相同 id 的旧条目和新条目。disabled、config、name、isolate 与 intercept 的变化成本不同，因此不会一律全量重启。

模块文件变化也可以触发 HMR，但模块重新导入只是更新信号。真正的替换仍要经过 Fiber 生命周期。

一次更新的四个阶段

  1. Loader 计算配置差异，确定哪些插件需要新增、停用、重载或保持。
  2. 候选模块被导入并验证，相关 Fiber 开始激活或退出。
  3. 运行时等待依赖变化和异步效应沉淀，得到 ACTIVE、PENDING 或 FAILED 等稳定结果。
  4. 候选成功后提交新配置；失败时保留或恢复旧插件和旧配置。

卸载为什么需要等待

提供服务的插件不能先销毁资源，再通知使用者。Fiber 会先停止对外供给，让依赖者感知服务不可用并退出；下游稳定后，提供者才逆序执行 disposer。

这段等待避免了最常见的半卸载状态：服务对象已经失效，但上层插件仍在发起调用。

失败时能恢复到什么程度

框架可以恢复配置选择、插件供给和已记录 effect 的调用顺序。外部世界是否真的回到原样，取决于每个 disposer 是否完整，以及外部操作本身是否可逆。

数据库写入、已经发送的网络请求或第三方系统状态，不能因为 Fiber 回到旧状态就自动撤回。插件仍要自行设计幂等和补偿。

关于 HMR

HMR 更适合被理解为“触发一次受控替换”，不是保存插件内部所有状态的魔法。组件内存会随旧 runner 退出；需要跨重载保存的数据，应放在替换边界之外。

在本页对应的基线中，web-app 明确关闭共享 HMR。浏览器侧重载仍应被视为能力边界。
